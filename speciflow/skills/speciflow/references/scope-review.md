# Scope review

Apply before authoring or adopting your own plan or work assignment, before
review/dispatch, and when selecting continuation after a method returns. Also
apply before claims of whole-outcome completeness. Use the existing gate,
report and native references; authority remains in [ownership.md](ownership.md).

## Check the proposed result

Read the original requirement, applicable upper obligations and later explicit
user decisions for this assignment. Bind them to the selected owner/root and
reviewed artifact. Compare the proposed work with those requirements before
checking agreement between downstream documents. Agent-authored plans, reviews
and passing selected tests do not amend approved intent.

Identify each omitted obligation and each proposed addition. Restore required
work under existing authority; use the amendment route in
[ownership.md](ownership.md#parent-contract-amendments) only for an actual
unresolved commitment change. Preserve independently authorized work and report
what remains incomplete. Missing required authority leaves only its dependent
conclusion unconfirmed.

## Select necessary work before adopting it

1. **Name the unchanged outcome and actual gap.** Use the inspected upper
   requirement and later explicit decisions. State what observable result this
   next action must produce for that outcome.
2. **Check your own additions.** For each proposed task, investigation, service,
   document, test, prerequisite or completion condition, identify its authority
   or demonstrated necessity. Compare a narrower sufficient action before
   adopting the proposal. A dependency of your chosen method is not automatically
   a dependency of the outcome. Plan text, sunk cost and reviewer agreement do
   not create that necessity.
3. **Choose the supported continuation.** Reject unnecessary layers and carry
   out covered work. A necessary bounded repair remains autonomous. If an
   approved technical contract itself must change, use the existing amendment
   route for that change and continue independently authorized work. Retain all
   mandatory outcomes; an easier adjacent fix cannot replace them.
4. **Bound the selected check.** In the existing plan/work record identify its
   acceptance question, source/input identities, observable result, finite
   effort/artifact boundary and stop conditions. Reuse available tools, source
   revisions and compatible environments. After each result, justify only the
   affected continuation. Stop on success, exhaustion, cancellation or repeated
   non-progress without new relevant evidence; retain the exact unmet outcome.
   A different worker, model, filename or directory does not reset the boundary.

When a test helper fails, first determine whether the original acceptance
question needs that helper at all. Prefer a direct adequate check using existing
observations/tools. Repair a necessary test with a bounded result; otherwise
remove that method's dependency from the proposed work through the applicable
route. Tests of a collector, adapter or its tests establish only that machinery's
behavior. They cannot stand in for the product correction or justify another
layer of verification. Preserve current evidence and cancellation instructions;
user-requested deletion makes affected claims unavailable, not passed.

A check that does not reproduce a defect limits that check's conclusion. Inspect
an already recorded incident's requirements, decisions, instruction basis and
actual contrary action before using it as RED. Preserve attribution and context
limits; another defect or a missing trace is not its RED. Assess the decision
of the actor who failed: recognition of a supplied bad proposal is not evidence
that the executor selects its own work correctly. Stop an unsuitable method
without turning it into a new prohibition on authorized repair or a completion
claim.

## Existing report and downstream handoff

Build the existing report in this order. The basis is working input to the
verdict, not metadata to append after the conclusion.

1. **Bind the assigned artifacts first.** Identify this assignment, gate and
   variant. The requested artifact and revision define the assignment: a path
   inside a supplied historical snapshot is provenance, not a request to review
   today's file or repair that live project. Use the supplied snapshot or retrieve
   its specified revision. A discovered current artifact does not replace this
   target or add a new assignment without applicable authority.
   Keep its source facts separate from other assignments in the same session.
   For every claimed defect, prerequisite or next action, identify the
   fact in this assignment's sources that supports it; a fact found only in a
   neighboring case cannot supply it. Fill compact basis rows before judging:

   | Role and assigned variant | Absolute artifact path or explicit owner/root | Available revision or content digest |
   | --- | --- | --- |

   Copy available identity and revision values from the inspected source; a
   field name or label is not a revision to reconstruct from memory. Check those
   literal values during final readback.
   Include the reviewed specification/plan and the evidence actually used.
   Record applicable upper authority and exact decisions. If a required source
   is unavailable, state that fact rather than inventing its contents.
2. **Derive findings for those rows only.** Compare the proposed work and
   completion claims with the assigned requirements and evidence. A result from
   another artifact or assignment does not establish this one's completion.
3. **Complete this report's four substantive parts.** Basis from step 1;
   purpose and the scope of the conclusion; findings with blockers/unknowns,
   identifiable mandatory remainder, prerequisites and concrete continuation;
   permitted next action and conclusions/effects still unproven. A positive gate
   decision alone does not establish this complete report contract.
4. **For an actual transfer, produce the next-worker handoff.** Carry the facts directly or link
   to the accessible complete bound report; keep this handoff's own assignment,
   retained obligations and limits explicit. Its assigned work must still serve
   the original requested artifact/purpose; separately discovered live-project
   defects are observations, not automatically this worker's next task.
   Use absolute local paths unless an
   owner/root is explicitly given. Resolve saved links from that file's directory
   and check their targets.
5. **Verify the final output before use.** Use the assignment's existing delivery
   form. For a conversation-only review, check the prepared response directly.
   When the assignment or existing process calls for saved report/handoff files,
   read their saved bodies after the last write. Compare every required part and claim
   against the basis rows and this assignment's actual sources, and check their
   links. Remove an asserted problem or remedy supported only by another case.
   Correct a missing binding, unsupported cross-variant claim or incomplete continuation
   under the existing review, then return to this readback step for the changed
   output. Deliver/use only the final verified output; a later replacement
   requires verification of that changed output. A conversation-only review
   requires neither a saved file nor a new worker assignment.

An unknown prior PASS target blocks reuse of that PASS, not a fresh current
review. Keep its provenance unknown. When the requested current assignment and
sufficient sources are available, explicitly select that current artifact in the
basis rows and complete the fresh warranted review now. Include the supported
handoff when actually transferring work.
Do not defer supplied-source inspection or output completion to a future worker.
If the current assignment's required facts really remain unavailable, hold only
that dependent conclusion and retain independent authorized work.

Neither a report nor its validation supplies amendment, projection or lifecycle
authority. An available content digest identifies the inspected artifact without
requiring another author version field.

For user approval of a written specification or implementation plan, read and
apply [the decision-block procedure](iterative-planning.md#present-a-specification-or-plan-for-approval)
before composing the approval request. This branch requires that reference even
when preparing a request is read-only rather than a native-owner mutation.

Keep the comparison ephemeral. Continue independently authorized work, including
covered repairs. Ordinary choices within approved scope need no new scope approval.
